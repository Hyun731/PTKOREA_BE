## 2. 개발하면서 지켜야 할 점

### 제품 원칙 (요청자와 합의된 것)
1. **사용자가 크게 불편하지 않을 것.** 입력이 몇 개 늘어도 빠르고 미리 채워져 있으면 괜찮습니다. 새 설정이 필요하면 먼저 시스템(기본값, 업종 프리셋, AI 추천)이 정할 수 있는지 보고, 세부 조정은 "그 밖의 설정" 같은 접힌 영역에 둡니다.
2. **자료를 자동으로 채택하지 않습니다.** 기획자가 모든 자료를 직접 확인합니다. 빠르게 확인하도록 돕는 것(요약, 의심 이유, 확인 후 "모두 채택")은 좋지만, 미리 채택하거나 자동으로 제외하면 안 됩니다.
3. **로그인이 필요한 정보는 절대 수집하지 않습니다.** 공개 페이지(커뮤니티, 커머스 리뷰, 광고 라이브러리, 포털)는 수집해도 됩니다. 로그인이 필요하면 "접근 불가"로 표시합니다.
4. **네이버 API는 쓰지 않습니다.** 키를 발급받을 수 없습니다. 데이터랩 대체안이나 키 발급 안내도 만들지 마세요. 블로그·카페·커뮤니티는 Perplexity 검색으로 찾습니다.
5. **비용 UI는 만들지 않습니다.** "약 $X 듭니다, 진행할까요?" 같은 확인이나 실행 한도를 넣지 않습니다. 비용은 원장(`RunLedger`)에 기록만 하고, 메인 화면의 팩트북별 총액으로만 보여 줍니다.
6. **디자인은 지금 것을 유지합니다.** 고객 문서에는 화면 배치나 필드 이름까지 적혀 있지만, 그건 참고만 하고 요구사항만 가져옵니다. 장표 품질 기준은 샘소나이트 v6 덱(Pretendard, 네이비 122648)입니다.
7. **고객용 덱에는 "자료 없어 빠짐" 장표나 문구를 넣지 않습니다.** 빠진 것은 내부 화면(초안·출력 화면의 빠진 장표 목록)에만 보입니다.
8. **자사 브랜드끼리 순위를 매기거나 평점을 나란히 비교하지 않습니다.**
9. **화면 문구는 쉬운 한국어로 씁니다.** 영어 용어나 개발 용어(QC, slot, entity 등)를 사용자에게 보이지 마세요.

### 코드 작업 규칙
- **git: rebase만 씁니다.** merge 커밋을 만들지 마세요. 커밋은 작게, 기능 하나씩, 메시지는 한국어로 무엇이 바뀌었는지 씁니다.
- **배포 DB 파일(`backend/var/dev.db`)을 맥에서 직접 열지 마세요.** 도커 컨테이너(`backend-api-1`)가 쓰는 중에 sqlite3 CLI나 파이썬으로 열면 "disk I/O error"로 서비스가 멈춥니다. 확인이 필요하면 `docker exec backend-api-1 python …`으로 합니다.
- **SQLite는 쓰는 쪽이 하나뿐입니다.** `RunLedger`는 별도 세션으로 기록하므로, 원장 호출 전에 진행 중인 트랜잭션을 `db.commit()` 하세요. 안 그러면 잠금 오류가 납니다.
- **외부 호출 응답은 7일간 캐시됩니다** (`ProviderCache`). 같은 요청을 다시 보내도 예전 결과가 나올 수 있습니다. 테스트에서는 캐시를 비우세요(`tests/integration/test_research.py`의 `clear_cache()` 참고).
- **AI 구조화 출력은 각 서비스 모듈의 `STRUCTURED` 리스트를 거쳐 호출합니다.** 테스트는 이걸 가짜 함수로 바꿉니다. 새 AI 호출을 만들면 같은 방식으로 만들고, 테스트 픽스처에 등록하세요(`aliases.STRUCTURED` 예시).
- **테스트는 실제 외부 API를 부르지 않습니다.** `PTK_SKIP_DOTENV=1`로 키 없이 돌리고, 수집기는 `httpx` transport를 가짜로 넣어 테스트합니다.
- **DB 칸을 더하면 Alembic 마이그레이션을 추가합니다** (`backend/migrations`). 서버가 시작할 때 자동 적용되므로, 칸을 더하기만 하고 지우거나 이름을 바꾸지 마세요.
- **장표 번호(slot id)는 브랜드별로 `-B1`, `-B2`가 붙습니다** (Phase 0에서 바뀜). 새 장표를 만들 때 `core/composition/build.py`의 `slot(..., part=...)`를 쓰면 자동으로 붙습니다.
- 프런트는 lint 스크립트가 없습니다. `npx tsc --noEmit`이 통과해야 합니다.
- 실제 키로 확인할 때는 **임시 DB에서 작게** 돌립니다. "다시 모으기" 같은 버튼은 실제 유료 검색을 부릅니다.

## 3. 이미 끝난 것 (Phase 0, `feat/feedback-p0`)

- **경쟁사 0건:** 브랜드·경쟁사·벤치마크마다 다른 표기(영문명 등)를 AI가 채웁니다(`Brand.entity_aliases`, `app/services/aliases.py`). 이름으로 거른 결과가 0건이면 다른 표기로 한 번 더 찾고, 그래도 없으면 `NO_MATERIAL` 오류로 빨간 "자료 없음"을 띄웁니다. "모두 확인 완료"에서도 빠집니다.
- **자사 브랜드별 구간:** 자사 브랜드가 2개 이상이면 자사·경쟁사·소비자·종합 장이 브랜드마다 따로 생깁니다. 나란히 비교하는 장표(1-1, 2-1, 2-2, 2-4, 2-5, 2-8a~d)는 앞쪽 "브랜드 비교" 장에 모았습니다.
- **빠진 장표 원인:** 채택 대기 / 수집 필요 / 설정 필요 / 업로드 필요로 나누고, 고치러 가는 버튼과 "빠진 자료 다시 모으기"를 붙였습니다. `access`(접근 불가)는 타입만 있고 아직 쓰는 곳이 없습니다. Phase 1의 커뮤니티·리뷰 수집에서 쓰면 됩니다.

### Phase 1-1. 브랜드 카드: 업종 + 공식 계정 (자사·경쟁사 모두)

```text
PTK 팩트북 서비스(backend/: FastAPI, frontend/: Next.js)에 작업해 줘. 먼저 backend/docs/HANDOFF.md의 "개발하면서 지켜야 할 점"을 읽고 지켜.

목표: 설정 화면의 브랜드 카드에 업종과 공식 계정을 추가한다. 사용자 입력은 최소로, AI가 미리 채우고 사용자는 확인만 한다.

1. 업종
   - Brand에 업종(industry)을 추가한다. 목록: 패션, 뷰티, 가전·IT, 생활용품, 식음료, 여행, 금융, 플랫폼, 통신, 자동차, 제약, 기타.
   - 업종마다 유형을 정한다: 리뷰 중심(패션·뷰티·가전IT·생활용품·식음료·여행), 지표 중심(금융·플랫폼·통신·자동차·제약), 둘 다 해당 가능.
   - 브랜드 이름을 넣으면 AI가 업종을 추천해 미리 고른다(app/services/aliases.py의 방식처럼 STRUCTURED 경유, 이미 정한 값은 덮어쓰지 않음).
   - 업종에 따라 조사 항목(app/services/scope.py)의 기본 켜짐이 달라진다. 리뷰 분석 항목은 Phase 2에서 생기므로 여기서는 연결 지점만 만든다.
   - 필수 항목(전자·뷰티·패션의 리뷰 분석)을 사용자가 끄는 것은 막지 않지만, 감사 기록(app/services/audit.py)에 "필수 항목 제외"와 사유를 남긴다.
2. 공식 계정
   - 지금 official_profiles는 자사 브랜드에만 있고 입력칸이 없다. 자사와 경쟁사 모두 등록할 수 있게 한다.
   - 브랜드 이름(과 entity_aliases)으로 후보 계정(Instagram, YouTube, Facebook, X, Threads, 블로그)을 찾아 추천하고, 사용자는 체크만 한다. 후보 찾기는 Perplexity 검색 + AI 판정으로 하고, 확실하지 않으면 후보로만 보여 준다.
   - "운영 안 함"과 "아직 등록 안 함"을 구분해 저장하고 화면에도 다르게 표시한다.
   - 경쟁사 공식 계정도 run_owned_item(app/services/research.py)이 수집하게 한다. 지금 수집기는 Instagram, YouTube만 된다. Facebook·X·Threads는 ScrapeCreators가 지원하는지 먼저 확인하고, 안 되면 "자동 수집 미지원"으로 표시만 한다.
3. 화면은 frontend/components/project-form.tsx의 기존 브랜드 카드 디자인을 유지한다. 업종은 카드 위쪽 한 줄, 공식 계정 후보는 체크 목록으로, 세부는 "그 밖의 설정" 접힌 영역에 둔다.

완료 기준: 테스트 추가 후 `PTK_SKIP_DOTENV=1 .venv/bin/python -m pytest -q` 전체 통과, frontend `npx tsc --noEmit` 통과, 임시 DB로 띄운 화면에서 브랜드 이름만 넣었을 때 업종과 계정 후보가 채워지는 것 확인. 마이그레이션이 필요하면 추가만 하고 기존 칸은 바꾸지 마. 기능 단위로 작게 커밋해.
```

### Phase 1-2. 인플루언서: URL 없이 찾기

```text
PTK 팩트북 서비스에 작업해 줘. 먼저 backend/docs/HANDOFF.md의 "개발하면서 지켜야 할 점"을 읽고 지켜.

목표: 인플루언서 조사 항목이 게시물 URL이나 해시태그를 직접 넣지 않아도 자료를 모으게 한다. 지금은 입력이 없으면 0건이고, 빠진 장표 원인이 "설정 필요"로 뜬다(app/services/missing.py).

1. 검색어는 시스템이 만든다: 브랜드 이름 + 다른 표기(Brand.names_for), 대표 제품명(있으면), 공식 해시태그(공식 계정 게시물에서 자주 쓰는 해시태그를 뽑아 쓴다).
2. 수집 경로
   - Instagram 해시태그: integrations/apify/client.py의 hashtag_posts, research.py의 discover_instagram을 재사용한다.
   - YouTube·블로그: Perplexity 검색(integrations/perplexity/client.py)으로 크리에이터 콘텐츠 URL을 찾고, 기존 수집기로 상세를 가져온다.
   - 로그인이 필요한 페이지는 수집하지 않고 건너뛴다.
3. 구분
   - 공식 계정(official_profiles)이 올린 글은 Owned, 다른 계정 글은 Earned로 나눈다.
   - 협찬 표기(#광고, #협찬, 유료광고 포함, paid partnership 등)가 있으면 협찬으로 표시한다.
4. 브랜드별 목표는 10건이다. 모자라면 항목 결과에 "수집 부족"을 남긴다(Phase 1-4에서 화면에 씀).
5. 사용자가 URL·해시태그를 직접 넣는 기존 방식은 그대로 둔다(있으면 그것도 같이 쓴다).
6. 자동 채택하지 말 것. 모은 자료는 후보(candidate)로 들어간다.
7. missing.py의 인플루언서 "설정 필요" 판정을 새 동작에 맞게 고친다.

완료 기준: 가짜 transport로 수집·구분·협찬 판정 테스트 추가, 전체 테스트 통과, 임시 DB에서 실제 키로 브랜드 하나만 작게 돌려 결과 확인.
```

### Phase 1-3. 카페·블로그·커뮤니티 수집 → 소비자 원문(VOC) 자동화 ★가장 중요

